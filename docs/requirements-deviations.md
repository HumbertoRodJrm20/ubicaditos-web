# Desviaciones de requisitos

| ID | Decisión | Motivo |
|----|----------|--------|
| HU-003 | Se excluye el inicio de sesión de pasajeros mediante JWT. La aplicación conserva la autenticación web de sesión con Laravel Breeze; no se agrega JWT ni inicio de sesión por tokens. | Ubicaditos es un monolito Laravel con autenticación de sesión. El alcance del backlog excluye HU-003 expresamente. |
| RF-10 | Si se omite `bus_id`/`route_id` se conserva el comportamiento histórico (autobús asignado y primera ruta). El autobús elegido puede estar asignado al conductor o disponible con `driver_id = null`, pero no puede tener ya un viaje activo. | Mantiene compatibilidad con el formulario existente y permite usar unidades libres sin crear una asignación permanente. El servidor valida la combinación aunque el selector filtre opciones. |
| RF-12 | No se agregaron columnas ni migraciones: se usan `trips.distance_km` y `trips.path_taken`, que ya existían. El trayecto se limita a 2000 lecturas `{latitude, longitude, recorded_at}` y sin lecturas se guarda `0.00` con `path_taken = null`. | El esquema actual ya soporta el requisito; el límite evita JSON ilimitado en viajes largos y mantiene SQLite/PostgreSQL sin cambios de DDL. |
| RNF-02 | La calificación sin `trip_id` se vincula automáticamente al último viaje completado del conductor; si se envía `trip_id`, debe estar completado y pertenecer a ese conductor. Los endpoints `/api/*` en tiempo real, incluido `GET /api/stops/{stop}/eta`, declaran `roles:admin,driver,passenger` y `/api/share/{token}` continúa público. | El formulario histórico no pide el viaje, así que exigirlo de forma estricta rompería clientes existentes; la regla de negocio se aplica en servidor. La matriz se hace explícita sin reducir el acceso de los tres roles ya soportados. |
| HU-30 / RF-30 | La ETA es una estimación sencilla: distancia Haversine en línea recta entre la última posición y la parada, velocidad media de 20 km/h, sin tráfico y redondeo al alza. No se consulta OSRM en tiempo de petición. Cuando la posición tiene más de cinco minutos o no hay autobús, `eta_minutes` es `null` y se muestra un aviso «aproximado». | El backlog pedía banderas de incertidumbre y una fórmula, pero no define motor de rutas en caliente ni umbral de tráfico. Reutilizar Haversine mantiene una sola definición de distancia y evita depender de un servicio externo en cada consulta. Además, `xd.md` afirmaba que ya existía una consulta ETA por parada; el código sólo tenía un cálculo local en JavaScript sin endpoint, por lo que se implementó el contrato servidor. |
| HU-014 | No existe GPS verdadero en segundo plano. El navegador mantiene la pantalla encendida con Wake Lock sólo cuando lo soporta; si el usuario oculta la pestaña, cambia de aplicación o bloquea la pantalla, el rastreo puede detenerse. La interfaz lo advierte explícitamente. | Es una limitación del navegador, no del servidor. Prometer seguimiento en segundo plano sería engañoso; por eso se conserva el aviso y se documenta el alcance real. |
| HU-012 | «Avísame» guarda una preferencia in-app (autobús + parada) de forma idempotente y privada. No hay push externo, correo ni SMS, ni un worker que envíe notificaciones en esta entrega. | El plan fija notificaciones sólo in-app y el backlog no define un canal externo ni su infraestructura. Se entrega el contrato de suscripción para que la futura entrega de avisos reutilice el mismo registro. |
| RNF-08 | `buses.accuracy`, `location_shares.bus_id` y `bus_stop_subscriptions` se agregaron con aprobación del propietario del 2026-11-25. Las columnas son nullable donde clients antiguos pueden omitirlas; el valor se valida en servidor. Las migraciones se ejecutaron en SQLite en memoria durante las pruebas y usan DDL portable, pero no se aplicaron contra PostgreSQL ni contra el SQLite de desarrollo. | El entorno dispone de PostgreSQL para producción, no en esta sesión de verificación. Se registra la limitación en lugar de afirmar una ejecución no realizada. |
| HU-024 | Se conserva la validación actual: descripción obligatoria con máximo 1000 caracteres, aunque la historia pida opcional y 500. | El plan aprobó mantener el criterio de la máster 4.5 (descripción validada) y documentar la desviación; cambiaría contratos y pruebas existentes sin una decisión nueva del propietario. |
| RF-19 | El límite acordado es de 5 reportes de emergencia por hora y usuario, aplicado con `RateLimiter` (`emergency-report:{user_id}`, ventana de 3600 s). Los pasajeros pueden omitir unidad y coordenadas; si el conductor omite ambos, conserva el default heredado de su unidad asignada. | El propietario aprobó el límite y el plan pedía evitar spam sin romper el flujo histórico del conductor. |
| HU-025 | El listado público expone sólo categoría, descripción, ruta/unidad opcionales y coordenadas; no incluye nombre, correo, `user_id` ni la relación `user`. La descripción obligatoria de 1000 caracteres se mantiene según la desviación HU-024. | La visibilidad pública es ciudadana y no debe revelar al reportante; cambiar la validación de HU-024 requeriría una nueva decisión del propietario. |
| HU-027 | El tope de cinco favoritos se valida en servidor (422 en JSON), con `position`/`label` en `favorite_routes`; al quitar un favorito se compacta la numeración. Las filas existentes recibieron su orden histórico durante la migración. | El propietario aprobó el tope; la tabla pivote ya existía y una migración con columnas nullable permitió conservar los favoritos actuales sin borrarlos. |
| HU-034 | Se implementó únicamente el promedio global de calificaciones con estado vacío. No se construyó el widget de actividad comunitaria. | `xd.md` condiciona ese widget a HU-017/HU-018, que no tienen criterios de aceptación en el backlog; inventarlos saldría del alcance verificado. |
| RF-19 / HU-025 / HU-027 (migraciones) | `incidents.route_id/bus_id/latitude/longitude/is_public` y `favorite_routes.position/label` fueron aprobadas por el propietario el 2026-11-25. Las migraciones se ejercitaron en SQLite en memoria; no se aplicaron a PostgreSQL ni al SQLite de desarrollo. | El entorno de verificación no dispone de PostgreSQL y no se debía migrar la base local sin autorización; el DDL usa tipos e índices portables de Laravel. |
| HU-007 | No se implementó 2FA/TOTP. El acceso administrativo depende únicamente de la sesión Breeze y del middleware de rol; los accesos por perfil del login son sugerencias visuales que nunca elevan privilegios. | El backlog marcaba la decisión como pendiente y el alcance acordado para el monolito fue documentar la omisión en lugar de introducir un segundo factor sin criterios ni infraestructura definidos. |
| HU-002 | La verificación obligatoria se aplica sólo al rol `passenger` y, además, está desactivada por defecto mediante `EMAIL_VERIFICATION_ENABLED=false`. Conductores y administradores conservan el flujo histórico; cuando el interruptor está en `false`, el registro de pasajeros marca `email_verified_at` y no envía `VerifyEmail`. | El propio `xd.md` fijaba como default no exigir verificación a otros roles, y el propietario pidió desactivarla para probar con correos ficticios creados en base de datos. El valor se lee en `config/auth.php` y puede activarse con la variable sin tocar código. |
| HU-030 | El selector de idioma cubre únicamente el "chrome" de la interfaz (textos de login, registro de conductor, preferencias y mensajes de sesión); no se tradujeron las vistas completas de rutas, mapas ni reportes. | El plan aprobó ese alcance por defecto. Traducir toda la aplicación exige un inventario de cadenas y revisión lingüística fuera del backlog verificado. |
| HU-030 / HU-041 / HU-005 (migración) | La migración `2026_11_25_000007_add_onboarding_settings_to_users_table.php` fue aprobada por el propietario el 2026-11-25. Agrega columnas de aprobación/licencia/preferencias a `users` con defaults compatibles (`approved`, `false`, `es`) y backfill de conductores; se ejercitó en SQLite en memoria pero no se aplicó a PostgreSQL ni al SQLite de desarrollo. | Se siguió la regla de pedir aprobación antes de crear migraciones. Los defaults preservan cuentas existentes y el entorno de pruebas no dispone de ejecución contra PostgreSQL; afirmar lo contrario sería evidencia no producida. |
| RNF-11(a)/(c) | Se inventariaron los bloques JavaScript inline y los seeders no invocados, pero no se extrajo código a módulos Vite ni se eliminó/archivó físicamente ningún seeder. | La extracción de mapas y formularios cambiaría comportamiento sin una revisión de navegador que no se ejecutó; borrar seeders históricos requiere caracterización y aprobación, no sólo inspección. El inventario quedó en `docs/maintainability.md`. |
| RNF-13 | Se implementaron `backup:database`/`backup:restore` sin paquete nuevo. Se probaron contra un archivo SQLite temporal con `Storage::fake('local')`; no se ejecutaron `pg_dump`/`pg_restore`, ni se respaldó/restauró la base de desarrollo real. | El entorno no cuenta con PostgreSQL ni con evidencia de ejecución de esos binarios; documentar la ruta implementada sin afirmar que se verificó evita una garantía falsa. La programación en Docker/IONOS queda fuera de alcance. |
| RNF-15 / HU-033 | La evidencia es estructural (HTML renderizado): idioma, etiquetas, `aria-label` y clases `dark:`. No se midió contraste, no se probó teclado/lector de pantalla y no se generaron capturas a 375×667 ni 1366 px. | No se ejecutaron Selenium ni revisión manual de navegador. Las pruebas automatizadas no pueden acreditar percepción visual ni foco real; `docs/accessibility.md` deja el checklist pendiente. |
| RNF-06 / RNF-14 | No se ejecutó k6 ni una prueba de latencia con cliente Reverb. Quedan sin resolver el umbral p95 de la sección 4.2 y la lista de navegadores acordada; no se inventaron valores. | No hay k6 en el entorno verificado y el umbral/lista requieren decisión del propietario. Se registraron pruebas funcionales y una guarda de N+1 como evidencia parcial, no como medición de carga. |
| HU-034 | Sigue parcial: el promedio global ya está en el dashboard, pero el widget de actividad comunitaria depende de HU-017/HU-018, cuyos criterios de aceptación no aparecen en `xd.md`. | No se inventaron criterios ni métricas para llenar el vacío del backlog; la fila se mantendrá bloqueada hasta que el propietario defina esa dependencia. |
